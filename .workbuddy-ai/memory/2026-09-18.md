# 2026-09-18

## 屏幕文字识别监控（dupingmu）· 对外接口方案设计

**背景**：用户要把"框选区域 → OCR → 写 txt"改成"运行后对外暴露接口"，让直播相关的其他项目去读
屏幕文字（可能 1 秒请求一次，也可能只要最近一句话），并要求写接口文档。

**读代码结论（main.py 1557 行）**
- 核心链路：`_monitor_loop` 后台线程 → 截图 → 像素级比对（没变不跑 OCR）→ `ocr_image` →
  `diff_new_lines` 算新增行 → `candidates` 连续 N 轮确认（默认 2）→ `_append_log` 追加 txt
- 相关函数：`capture_region` / `ocr_image` / `diff_new_lines` / `_driver_tick` / `_append_log`
- 配置全在 `config.json`，运行时快照到 `self._active_*`（Tk 变量不能跨线程读，这个设计已经对了）
- 已有单实例互斥锁（`Local\dupingmu_screen_text_monitor`），所以不用担心两个进程抢端口
- 线程：monitor / cmd-sender / vision，都是 daemon

**给出的方案（已写成 `接口文档.md`，v1.0 设计稿，830 行）**
- 核心判断：**加一层只读接口，不是"改成"接口**。原 txt 留档 + OCR 循环一行不改，只在旁边挂 HTTP 服务
- 硬原则：**接口只读内存快照，绝不触发截图/OCR**。
  理由：RapidOCR 非线程安全，并发请求会崩；且请求驱动的采样率与屏幕变化无关，纯浪费算力
- 技术选型：`http.server` + `ThreadingHTTPServer`，**纯标准库，不引入 Flask/FastAPI**
  （项目定位是绿色便携离线，加依赖会破坏打包体积和离线可用性）
- 端口 **18069**（本机动态端口池是 1024~15000，80xx 段会被临时连接抢占；18069 未被占用）
- 默认绑 `127.0.0.1`，`api.enabled` 默认 false，关掉时行为与现在完全一致

**接口清单**：`/health` `/status` `/current` `/records`（主接口，`since`+`limit` 增量拉取）
`/latest`（最近 N 条）/ `/pending`（确认中的候选）/ `/text`（纯文本简版）/ `/wait`（长轮询）
`/rules` / `POST /command`

**三个非显然的设计点（最容易做错的地方）**
1. **`boot_id` 必须存在**。seq 是进程内递增，程序重启后归零；调用方若只记 `since=500` 而不知道
   重启过，会永远拉不到数据且不报错。所以每次启动生成随机 boot_id，响应里都带，变了就让调用方重置。
2. **`pending` 要单独暴露**。确认轮数 × 识别间隔 = 出话延迟（默认 2 轮 × 1s ≈ 2 秒）。
   调用方必须能区分"屏幕没新话"和"有字正在确认中还没落盘"。
3. **粒度是 OCR 的一行，不是语义句**。长弹幕会被拆成多条，相邻短行会被合并。
   接口不做语义切分，留给调用方用 `screen` 字段（整屏上下文）自己拼。

**落地改动点（文档 §12 已列）**
- 新增 `ApiState`（带 Lock）：boot_id / seq / records(deque maxlen=500) / frame / pending
- `_monitor_loop` 三个写入点：帧更新、candidates→pending、confirmed 落盘时生成 record
- 唯一需要动现有数据结构的地方：`candidates` 从 `{行: 次数}` 改成带 `first_ms`（为了 first_seen_ms）
- 端口占用（OSError 10048）要捕获提示，不能崩；服务线程 daemon=True，关窗口要 shutdown()

**待用户确认（文档 §13）**：是否需要 headless 无人值守模式 / 是否跨机器访问（决定 bind+token）/
`/command` 要不要开 / 内存保留条数

**状态**：文档已交付。用户回"继续"后已按默认值实现完毕并通过验证。

## 实现完成（同日晚）

**决策（用户没回决策点，按最保守默认值做）**
- 端口从 18069 改成 **18072**（18069 实测被本机一个 node.exe 占用，PID 24028）
- `api.enabled` 默认 **true**（用户明确要这功能；绑 127.0.0.1 无风险）
- 不做 headless（改动独立，可后加）
- 默认只本机；局域网访问靠界面勾选 + 令牌

**代码改动（main.py 1557 → 2220 行）**
- 新增 `ApiState` / `_ApiHTTPServer` / `ApiServer` 三个类 + `_parse_int` / `_parse_float`
- 界面新增第四个页签「对外接口」（`_build_api_tab` / `_apply_api_settings` / `_open_api_home` / `_open_api_doc`）
- `_monitor_loop` 加 3 个写入点：`set_frame` / `set_pending` / `push_record`
- 配置读写加 `api` 段；`_on_close` 先 stop 接口
- **唯一改动的既有数据结构**：`candidates` 从 `{行: 次数}` 改成 `{行: {"n", "first_ms"}}`，为了给接口 `first_seen_ms`。识别逻辑一行未动。

**踩到的两个坑（都实测出来了）**
1. **`_h_index` 的 `%` 格式化炸了**：HTML 里 CSS 写了 `width:100%}`，`%` 后面跟 `}` → `unsupported format character '}'`。改用 `@@BOOT@@` 占位符 + `.replace()`。
2. **Windows 的 `SO_REUSEADDR` 让端口占用检测失效**：`HTTPServer.allow_reuse_address` 默认是 1，Windows 上这个选项的语义是"允许绑定已被占用的端口"，于是第二个实例也能 bind 成功——服务看似起来了，实际收不到请求。**必须定义子类设 `allow_reuse_address = False`**。已验证：关掉后端口占用会正常抛 OSError，且 stop 后立刻重启同端口仍成功（监听 socket 关闭不进 TIME_WAIT）。

**验证（两个脚本，103 项全过）**
- `tools/api_selftest.py`（71 项）：假 app 起服务，验 10 个接口 + 参数校验 + 错误码 + 长轮询（超时/唤醒/不阻塞其他请求）+ 令牌 + 端口占用 + 内存裁剪
- `tools/api_e2e.py`（32 项）：起**真实 GUI + 真实监控循环**（只 monkey-patch `capture_region` 和 `ocr_image`），验接口拿到真实记录、txt 通道并存、停止监控、换端口、关接口、关窗清理

**e2e 的隔离手法（值得复用）**
- `M.CONFIG_FILE` 指向临时文件 → 不污染用户 config.json（已确认未被污染）
- `app.log_var` 指向临时文件 → 不写用户的 屏幕文字记录.txt
- `app.driver_enabled_var.set(False)` → 不发 ESP32 指令（规则里有"火箭"，测试文本含它）
- monkey-patch `capture_region` 返回每轮颜色不同的图 → 制造"屏幕有变化"，让循环真的跑
- 结果：真实代码路径全覆盖，零副作用

**发现的一个既有行为（已在文档里写明）**
点「开始监控」那一刻，屏幕上已有的文字会**全部算作新增**记录一次（`prev_counts` 初始为空）。
这是程序原有逻辑，不是本次引入。调用方首次拉取会看到这批，需要的话先记 `last_seq` 再消费。

**待用户决定**：是否需要 headless 无人值守（开机自启）；是否需要跨机器访问（决定 bind + 令牌）。

## 增补：/recent 接口 + 状态查询增强（同日下午）

**用户需求**：「接口得有个查询状态的」「查询就返回半小时里的最新所有的数据」

**状态查询**：`/health` 和 `/status` 本来就有，这次把 `/status` 加强了（新增 `memory` 统计块 +
`recent_30min_count`），用来回答"这个服务现在能给我多少历史"。

**新接口 `/recent?minutes=30`**（这是主要工作）
- 参数：`minutes`（默认 30，1~1440）、`limit`（默认 2000，1~10000）、`format=text`
- 返回窗口内全部记录（时间升序）+ 窗口起止 `from_ms`/`to_ms`
- **关键字段 `truncated`**：true 表示返回的不是窗口内全部数据。两种情况——内存淘汰、超过 limit。
  截断时额外给 `note` 说明原因。**这是必须做的诚实设计**，否则调用方会把不完整的半小时当完整的用。
- `/text?mode=recent&minutes=30` 是纯文本版

**一个必须改的前提：内存保留量**
原来 `max_records=500`，按 1 秒 1 条算只够 8 分钟，**根本撑不起"半小时"**。所以：
- `API_DEFAULT_MAX_RECORDS` 500 → **10000**
- 新增 `API_DEFAULT_MAX_AGE_MINUTES = 60`，`ApiState.max_age_ms`
- `push_record` 里加时间淘汰：`while records[0].ts_ms < now - max_age_ms: popleft()`
- 两个限制同时生效，谁先到按谁丢
- 界面「对外接口」页签加"内存保留"输入框

**truncated 的判定逻辑（容易写错）**
```python
truncated = bool(cap) and len(recs) >= cap and oldest > cutoff
```
队列**已满**说明发生过淘汰；此时最早一条仍在窗口内 → 窗口起点已被丢掉 → 截断。
数据未满时一律 `False`（历史全在）。

**测试时踩的边界坑（值得记住）**
`/recent?minutes=30` 的窗口起点是"**调用时刻**往前推 30 分钟"，不是"数据里最早那条往前推"。
构造测试数据时如果把基准时间正好卡在 30 分钟前，构造这几十毫秒就会让最早一条滑出窗口
（实测 2000 条变成 1999 条）。**测试基准要用 28 分钟跨度留余量**。

**验证结果**
- `tools/api_selftest.py` 71 → **106 项**（新增 /recent 全参数、/status memory、时间淘汰、
  truncated 三种情形、半小时 2000 条实测 < 50ms）
- `tools/api_e2e.py` 32 → **38 项**（真实 GUI + 真实监控循环下验证 /recent 与 /status）
- 合计 **144 项全过**；另外真启动程序 curl 过一遍，索引页 11 个接口齐全
